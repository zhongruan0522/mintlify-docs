## Description

Backend management interfaces adopt a multi-level authentication mechanism, commonly: **Public**, **User**, **Admin**, **Root**.

## Authentication Methods (Choose One)

### Session

Obtain Session via the login interface:

- `POST /api/user/login`

### Access Token (Recommended)

Carry in the request header:

```text
Authorization: Bearer {token}
```

Tokens can be generated in "Personal Settings - Security Settings - System Access Tokens".

## Required Request Headers

Some interfaces require carrying a user identification request header:

```text
New-Api-User: {user_id}
```

Where `{user_id}` must match the currently logged-in user.

## Permission Levels

- **Public**: No authentication required
- **User**: Requires login or Access Token
- **Admin**: Requires administrator privileges
- **Root**: Highest privilege

## Access Token Scope

Access tokens grant **User-level API access only**. Even an administrator account cannot call Admin or Root endpoints with an access token; the server rejects such requests regardless of the account's role. Use a session cookie for console operations that require admin privileges.

## Session Invalidation on Credential Changes

Sessions are re-validated against the database on every request, so credential changes invalidate existing sessions immediately:

- A password change, disabling 2FA, or other credential changes bump the account's `auth_version`; older sessions are rejected with HTTP `401` and the message `Session expired, please log in again`.
- Banning or role changes take effect on the affected session's next request as well, forcing a re-login.
- After upgrading NookMux, sessions issued by an older version fail the same `auth_version` check once; a single re-login is expected.
